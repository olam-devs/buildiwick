# Buildiwick — Agent Context

Read this before making changes. It's written for whichever AI agent picks this codebase up next — you weren't in the room for the decisions below, so this is the room.

## What Buildiwick is

A Dar es Salaam construction company running 16 active projects out of one shared Excel workbook. The client's mandate is explicit: **digitize what they already have, don't redesign it.** Every table, category, status field, project name, and dollar figure in this codebase's seed data traces back to their real interim tracker (`Buildiwick_All_Projects_Interim_Tracker_4.xlsx`, in their original brief materials) and their process lifecycle document. Don't invent data or restructure the schema on aesthetic grounds — if something looks odd, it's probably a faithful digitization of something odd in their real process, not a bug.

Full scope reasoning lives in the **Build Phases** artifact (https://claude.ai/artifact/Aj3baTbHdXgCmHQVxhZyKD). The original Phase 1 transaction UI/API remains in place. Normalized workflow records and web workflows now cover estimates, internal budgets, expense requests/approval history/payments, clients, invoices/client payments, phases, project documents, Accountant reporting, and Director analytics. Sales/procurement remains future scope.

## Current state of the code

- **Schema**: `app/database/migrations` — the Phase 1 roles/users/lookups/projects/assignments/labour_agreements/transactions, plus normalized workflow tables (clients, project_phases, project_estimates/estimate_entries, internal_budgets/internal_budget_entries, expense_requests/approvals/payments, client_invoices/items/payments, project_documents).
- **Models**: `app/app/Models` — straightforward Eloquent, see `Project::categoryTotals()` and `LabourAgreement::paidToDate()/outstanding()` for the computed-not-stored pattern.
- **Auth & authorization**: Sanctum tokens for `routes/api.php`, session guard for `routes/web.php`. Policies in `app/app/Policies`, one per gated model. `AppServiceProvider::boot()` has a `Gate::before` that blocks deactivated accounts outright and bypasses everything for Admin, plus a `view-dashboard` Gate that isn't tied to any one model.
- **Web UI (the real product)**: `app/app/Http/Controllers/Web` + `app/resources/views`. Session-authenticated, server-rendered Blade. This is what a human actually opens — the API exists for a future PWA/offline client, not as the primary interface.
- **Shared creation logic**: `app/app/Services/TransactionRecorder.php`. Both `Api\TransactionController` and `Web\EntryController` call this — it's the one place a legacy transaction gets created, so the labour-instalment-is-already-paid rule and offline `client_uuid` idempotency check can't drift. New workflow payments use `ExpensePaymentRecorder` and `ClientPaymentRecorder`; do not update cumulative legacy payment fields for those records.
- **Visual identity**: Inter font, Frappe's actual blue (`#2490EF`), status shown as a colored dot + text. This was a deliberate pivot after two earlier visual directions were rejected as "still looks AI-generated" — the brief was to match Frappe's real Desk UI, not an original interpretation of it. Don't reintroduce a different accent color or font without checking with the human first; this was already litigated once. The client's logo (the blue BW mark, `public/images/buildiwick-mark.png` and its favicon/icon sizes) is the brand mark in the sidebar, sign-in page and every Excel title band (`ExcelExportService::brandBand`); it does not change the UI accent colour.

## Decisions already made — don't relitigate these

- **Legacy labour instalments remain `transactions` rows.** In the Phase 1 ledger they have `agreement_id` set and `main_category = labour_subcontracts`; `TransactionRecorder` retains its existing behavior. The new expense-request workflow is separate and records outgoing payments as individual `expense_payments` rows.
- **A legacy labour instalment IS the payment event.** In the Phase 1 ledger, `amount_paid_received = total_amount` and `payment_status = 'paid'` are set at creation time in `TransactionRecorder`. This historical behavior does not apply to new expense requests/payments, which have separate approval and payment records.
- **Estimate markup is distinct from the internal budget.** `estimate_entries.base_unit_cost` and `markup_percent` represent the underlying estimate rate and markup; client unit price, base total, markup amount, and client total are computed with fixed-point arithmetic. Internal budget entries are a separate unmarked-up dataset.
- **New payments are individual audited rows.** Expense and client payment write paths must call their transactional recorder services, which lock and reread the payable parent, check current outstanding amount/status, and then insert the payment with actor/evidence data.
- **`payment_status` and `data_status` are separate axes**, both real columns on `transactions`. Don't collapse them — a row can be `paid` and still `needs_confirmation` (this is literally true of all 33 imported Kinondoni rows).
- **One `lookups` table, not nine.** Columns: `type`, `code`, `label`, `parent_type`/`parent_code` (for subcategory→main_category), `sort_order`, `is_active`. Query with `Lookup::ofType('unit')` or filter by `parent_code`. Don't add a new physical table for a new dropdown list — add rows here.
- **Construction units remain one shared lookup.** Category-aware unit lists are recommendation-first ordering only; forms retain every active valid unit as a fallback, and historical unit codes must not be removed or renamed.
- **Site requests begin as need reports, not priced requests.** New Site Operator HTTP writes leave commercial fields null and ignore crafted supplier/rate/total input. Legacy priced requests remain readable; PM commercial preparation uses separate nullable fields and reusable `SupplierPayee` records, restricted to PM/Admin. Approval/rejection and payment remain Phase 6.
- **PM Phase 6 decisions are transactional and snapshot commercial instructions.** Approval/rejection locks a pending request, records an `ExpenseRequestApproval` with supplier/payment snapshots and decision notes, and approval never creates an `ExpensePayment`. Approved commitments use approved commercial totals; payments remain a later Accounts realization.
- **ExpensePayment is actual outgoing expenditure.** Accountant payments are separate immutable event rows recorded only against approved requests; paid, outstanding, and payment status are derived from those rows. Approval alone is not expenditure, and payment evidence is private.
- **ClientPayment is actual incoming cash.** ClientInvoice totals and receivables remain separate from ClientPayment events. Recorded cash balance is ClientPayments minus ExpensePayments; it is not profit, and draft invoices do not count as receivables.
- **Accountant reporting is a projection over payment events.** Transaction registers include only `ClientPayment` and `ExpensePayment`; invoices, requests, approvals, estimates, and budgets are context, not cash transactions. Same-date ordering is payment date, recorded timestamp, then ID. Payable aging is age since approval unless a true due date is added later.
- **Director is a distinct oversight role, not the Admin bypass.** The seeded Director account receives organization/project analytics and is the required verifier for PM internal-budget versions; it does not receive Accountant payment writes or general Admin bypass access. A PM submission remains `finalized` (awaiting review), can be returned to `draft` with notes, and becomes the active baseline only at `approved`. Director current-position metrics are separate from date-filtered activity; budget utilization compares actual `ExpensePayment` outflows and approved commitments independently against the Director-approved internal budget.
- **Site request prices begin with the PM.** Site Operators submit request type, description, quantity/unit, and specifications only; all submitted Site `requested_amount` values are ignored. New batch requests must be allocated to an exact entry in a Director-approved internal budget before PM approval can send them to Accounts.
- **One request batch can contain many supplier groups and items.** The Site Operator or PM creates the complete item list; during commercial preparation the PM assigns each item to its internal-budget line, supplier/payee, price, and payment instruction. Items sharing a supplier are presented as one group, while the complete request total sums every group. Accounts sees only the PM-approved commercial grouping—not the Site-origin request section. Supplier details and payment controls live inside each group, while payments and budget usage remain item-level for auditability.
- **Operational exports are real Excel workbooks.** Director, Accountant, PM request/labour, Estimator estimate, PM internal-budget, and client-invoice downloads use formatted `.xlsx` files with typed money/date cells; CSV is no longer the user-facing export format.
- **Budget and estimate edits are audited immutable revisions presented as normal edits.** PMs use **Edit Internal Budget** and the Director/Admin uses **Edit Estimate**; the service copies the approved/issued document into a draft and retains the prior version. Opening the edit and every subsequent line add/change/delete on an edited version requires a justification. `project_edit_logs` retains the actor, reason, document/version, item and before/after values, and the combined project log is visible to the Director.
- **An estimate leaves the Estimator's hands at submission.** Lifecycle is `draft → submitted → issued`. The assigned Estimator/QS may edit only a draft whose `editor_role` is not `admin` (their own, or one the Director returned). After **Submit to Director** they have read-only access, and later Director revisions are hidden from them. The Director/Admin may edit a submitted estimate in place, approve and issue it, return it with required `review_notes`, start an estimate themself, or revise an issued one. Only `issued` estimates feed invoicing and analytics. Excel template upload (`EstimateTemplateService`) replaces all lines of the working estimate after validating every row, and follows the same edit permissions.
- **Ongoing projects are onboarded per project through Opening Records (`OnboardingRecordsService`).** One project-specific workbook (Expenses / Client Invoices / Client Payments) is fully validated, then becomes approved `ExpenseRequest`s (approval stage `onboarding_import`, dated on the expense date) with payments via `ExpensePaymentRecorder`, issued `ClientInvoice`s with historical dates, and receipts via `ClientPaymentRecorder`. Every created row carries `onboarding_import_id`. Do not onboard history into the legacy `transactions` ledger, because it does not feed Accountant or Director reporting. Imports are Accounts' (Director through the bypass) and can be undone only while no newer payment depends on them.
- **Director KPI targets and warning rules are thresholds over existing analytics, not new figures.** `DirectorKpiService` measures `director_kpi_targets` (company or project, any period) using `DirectorAnalyticsService` portfolio rows and summaries; `ProjectWarningService` applies `project_warning_rules` (project_id null = company default; project rows override; built-in defaults until saved) to the same project rows. Only the Director role (Admin via bypass) may write them (`manage-director-strategy`). Review periods and their comparison periods come from `App\Support\ReviewPeriod`. Scope stays visible in navigation: company targets and default rules appear only in the Director's main sidebar; a project's targets, warnings and limits appear only inside its workspace (**Warnings & KPIs**).
- **Phase 1 runs in recording mode (`BUILDIWICK_MODE=recording`, the default).** Only Director, PM and Accounts use the system. Client billing, estimates, the Site Operator role and the approval workflow are switched off by `config/buildiwick.php` features and `feature:*` route middleware, which returns 404; their code stays for later phases. Tests run with `BUILDIWICK_MODE=full` (`phpunit.xml`); recording-mode tests switch it on themselves. Never show client invoices, receipts or receivables in recording mode, not even as optional screens.
- **Recording mode uses one per-project ledger (`LedgerController`, `ExpenseLedgerService`, `LedgerAnalyticsService`).** Every line is an approved `ExpenseRequest` with approval stage `recorded` (or `onboarding_import` for the tracker import), coded `<PREFIX>-TXN-NNNN` from the project code. The PM logs "To confirm" and Accounts (or the Director) confirms by recording an `ExpensePayment`; a remainder under TSh 1 counts as settled. Phases are a tree via `project_phases.parent_id` (max 3 levels, `PhaseTree`). Budgets are Director amounts per phase node × category, stored as approved single-line `InternalBudget`s (`PhaseBudgetService`). Workers are `labour_agreements`. Ledger totals are summed in integer cents. The live tracker is imported with `app:import-tracker`, which keeps every recorded value unchanged.
- **Recording-mode access is per user, not only per role.** `App\Support\Access` holds the permission list and role defaults. `users.permissions` (null means role defaults) and `users.all_projects` (or `project_assignments`) decide what a PM or Accounts user can do and which projects they open; the Director always has everything. Check the ledger gates (`record-expense`, `confirm-payments`, `deny-expense`, `manage-workers`, `manage-project-structure`, `export-ledger`, `view-ledger`), never role names, in new ledger screens. A denied line is `status = rejected` with a rejected approval row, and it is excluded from every total. Item suggestions are names only (`material_item` lookups per category); never pre-fill amounts from them. Totals and analytics are themselves a permission (`view_analytics`, gate `view-analytics`), off for staff: a staff Accountant only confirms and denies, a PM records, and neither sees project totals unless the Director ticks it. The Director's own ledger entries are recorded as paid, and only the Director may correct or delete a paid line (the payment is re-recorded and logged).
- **Recording-mode spend is confirmed spend.** `LedgerAnalyticsService` arrays keep the key `recorded` but it means confirmed (paid) amounts, as in the client's tracker totals; unconfirmed lines are `to_confirm` ("Awaiting confirmation") and never count toward spend, budget used or KPIs until confirmed. Imported "Material log - to confirm" rows are such lines. Company overheads ledgers (`projects.is_company_overheads`) are Director-only and excluded from project lists, totals, rankings, warnings, company KPIs and the all-projects export; `User::canAccessProject()` enforces it.
- **Labour agreement rows review existing requests; they do not create requests.** The final column links pending requests to PM review and completed requests as references. The dedicated labour-request Excel action filters the all-request export to `labour_subcontracts`; the separate agreement workbook remains available.
- **Director analytics reuse existing financial accessors and reporting services.** Do not add Director-owned monetary tables or competing total/outstanding formulas; estimate and budget values come from their current version lifecycles, invoice/request balances from their model computations, and cash event registers from `AccountantReportingService`.
- **Director historical snapshots are timestamp-based reconstructions, not invented audit history.** The calendar view uses recorded phase start/completion dates, estimate/budget lifecycle timestamps, request approvals, invoice issue dates, and payment dates up to end-of-day. The UI must disclose that an untimestamped historical status change cannot be reconstructed exactly.
- **Private uploads use the local private disk and authorized application downloads.** New evidence is stored on `local`; do not create public-storage URLs for evidence or documents. Existing legacy transaction evidence can be moved, preserving its stored relative path, with `app:secure-legacy-transaction-evidence --force` only after backup. This command verifies private copies before removing public copies and does not change transaction values.
- **Financial payment retries use idempotency keys.** Payment forms pass unique UUID keys; nullable unique columns preserve historical rows. Recorder services lock/recheck the payable/invoice and return the original event for a same-user/same-parent retry; row locking remains the concurrent overpayment guard.
- **Inactive accounts are blocked at authenticated web/API route middleware**, in addition to authorization. Role landing is exact-code allowlisted; missing or unknown role codes never receive the Admin dashboard fallback.
- **Site Operator has no index/show route for transactions at all**, checked in `TransactionPolicy::viewAny()` — not a route that returns 403, an ability that's simply never granted. The entry-form response for this role (`TransactionController::respond()` and the equivalent in `Web\EntryController`) echoes back only the fields just submitted. If you add a new endpoint this role can hit, apply the same rule: never return more than what they just typed.
- **Project codes and transaction codes are human-meaningful strings** (`BWG-KIN-2026-001`, `BWG-KIN-2026-001-TXN-0034`), not just internal IDs — they match the client's own reference convention. Don't replace them with UUIDs-only; the `client_uuid` column is separate and exists purely for offline idempotency.
- **The database is regenerable, not sacred.** `php artisan migrate:fresh --seed && php artisan app:import-kinondoni-historical-data` rebuilds it from scratch, deterministically, from the migrations/seeders/import command — not from a committed `.sqlite` file (which is gitignored). If you're testing something destructive, this is your reset button.
- **The one explicitly illustrative dataset is isolated in `DemoProjectSeeder`.** `BWG-DEMO-2026-001` and every related name, contact, account number and amount are fictional, labelled DEMO, and exist only for role-by-role training. Do not mix these records with the 16 tracker-derived projects or remove their visible demo labels.
- **Construction phases are project-specific, with the original seven retained only as a starter template.** The assigned Estimator/QS may add, rename, date, delete, or reset phases while the estimate is a draft. Issuing the estimate (or later approved financial activity) locks the phase structure. Draft estimate/budget lines are freely editable; mandatory reasons and immutable version history begin only after issuance/approval.
- **The Phase 1 `transactions` ledger remains a compatibility/history surface.** Estimate, internal-budget, expense-request/approval/payment, and client invoice/payment events are distinct records; do not silently reinterpret or delete old transaction rows. Their new `project_phase_id` is nullable so historical rows without a stage remain valid; only explicitly classified transactions should be linked to a phase. New expense-request outgoings use individual `expense_payments`, not the legacy cumulative payment column.

## Branching & deployment

- **`develop` is the integration branch.** All routine work should start on a feature branch and return to `develop` through review. The shared sandbox at **https://buildiwick.olamtec.co.tz** is checked out from `develop`.
- **`main` is the stable production-candidate branch.** Do not merge into it as part of ordinary sandbox development. A `develop` to `main` merge is an explicit release decision for the real production domain.
- **Sandbox deployment is manual.** Pushing to `develop` does not update the server automatically. An authorized operator must connect to the DirectAdmin host, pull `develop`, install changed dependencies, run new migrations, and refresh Laravel caches. Do not add an auto-deploy webhook without the owners' approval.
- **Production configuration is not stored in Git.** The server's `app/.env` must remain uncommitted. Back it up before rebuilding or replacing the checkout.
- **Demo logins** use password `password` only in local/testing and the shared sandbox: `director@buildiwick.test` (Director), `grace@buildiwick.test` (Accounts), `twalib@buildiwick.test` (Estimator/QS), `neema@buildiwick.test` (Project Manager), and `amani@buildiwick.test` (Site Operator). Production must use replacement credentials and must not expose demo hints.

## Contribution protocol

This is a two-developer team, each working with their own AI agent, sharing one repo. Work from a feature branch and target `develop`, not `main`, unless the owners explicitly approve a production promotion. Read `CHANGELOG.md`'s most recent entries before you start, so you're not rediscovering context the other side already has. Before you finish and push:

1. **Write a specific commit message.** What changed and why — "update files" or "fixes" tells the next agent nothing. Reference the real thing that changed: "add record-payment page for Accounts" not "update EntryController."
2. **Add a dated entry to `CHANGELOG.md`.** Plain language, written for a teammate (human or AI) who wasn't there: what you built or fixed, what's now possible that wasn't before, and any new decision that belongs in this file's "Decisions already made" section.
3. **If you made a real decision** (not just an implementation detail) that the other developer's agent would need to know to avoid redoing your reasoning or contradicting it, add it to this file, not just the changelog — the changelog is a log, this file is the current state of truth.
4. **Don't invent data.** Every project name, category, and figure in seed data should trace to the client's real materials unless a comment explicitly marks it illustrative.
